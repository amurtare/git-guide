## 용어

| 용어 | 뜻 |
|---|---|
| **단위(unit)** | 설계·구현을 나누는 기본 조각. 워크플로라면 실행 단계(노드), 앱이라면 기능·모듈, 라이브러리라면 API 묶음. 이 문서는 프로젝트 성격과 무관하게 "단위"라고 부른다 |
| **단위 ID** | 단위에 붙이는 안정 식별자(예: `U3`, `#4b`, `auth-login`). 문서끼리 서로 인용하는 키 |
| **설계 지도** | 모든 단위를 한 표에 늘어놓은 문서(`dev/design/map.md`) — 순서·분기·담당·참조 문서. 설계의 단일 소스 |
| **단계(step)** | 구현에서 한 번의 플랜→구현→검수→커밋으로 끝내는 작업 묶음(= `dev/impl/checklist.md` 항목 하나) |
| **Phase** | 구현 백로그(`dev/impl/checklist.md`)를 묶는 큰 구간. 여러 단계(step)를 담는다 |
| **플랜 검수 / 구현 검수** | 플랜 승인 전에 플랜을, 커밋 전에 코드·테스트를 독립 검수자에게 리뷰받는 것. 둘 다 GO까지 반복(§4-4 규칙 공통) |
| **외부 리뷰 보강** | Plan·Design 단계에서 독립 검수자가 낸 지적 중 아직 설계에 반영하지 않은 것의 목록(`dev/plan/checklist.md`). 누락 없이 반영해야 Design 완료 |
| **GO / NO-GO** | 검수 결과. GO = 차단급 지적(P0·P1) 없음 |
| **P0 / P1 / P2** | 검수 지적의 심각도. P0 = 데이터 손상·보안·되돌릴 수 없는 부작용 / P1 = 명세 위반·잘못된 동작·문서 간 모순으로 진행이 막힘 / P2 = 개선 권고(가독성·테스트 보강 등) |
| **구획** | 미검증 장부(`open-questions.md`)를 성격별로 나눈 묶음. 문자 하나(A, B, …)로 표시하고 ID의 접두사가 된다(`B3`) |
| **스모크** | 실제 환경에서 짧게 돌려 보는 확인. 부작용이 있으면 원상복구까지 한 세트 |
| **preflight** | 부작용 때문에 미리 검증하지 못하고 "첫 실사용 때 확인"으로 넘긴 항목 |
| **역전파** | 하위 문서를 바꾼 뒤 그 내용을 요약·인용하는 상위 문서에 되돌려 반영하는 것 |
| **핸드오프** | 다음 세션이 이 세션의 맥락 없이 이어받을 수 있게 남기는 상태 기록 |
| **공용 참조** | 독립 단위로 두지 않고 여러 단위가 함께 인용하는 규칙·모듈(예: 공통 검증 규칙, 공용 클라이언트) |
| **확정 전제** | 구현 시작 시점에 고정하는 프로젝트 조건 — 절대 규칙·언어/런타임·외부 시스템·실행 환경 제약·스모크 표준 대상·검수자. `dev/impl/README.md`에 둔다 |
| **구현 준비 상태 점검** | Design → Impl 전환 직전에 한 번 하는 세션. 가정 실측·문서 간 어긋남 제거·확정 전제 작성·백로그 편성을 확인한다(§0-6) |

## 0. 전체 생애 — Plan(계획) → Design(기획·설계) → Impl(구현)

구현만 잘 굴려도 **앞단이 흔들리면 구현 중에 설계가 계속 뒤집힌다.** 그래서 앞단도 같은 원리
(저장소 안 문서가 기억 · 확정과 미결의 분리 · 단계 게이트)로 굴린다.

```
 ┌─ Plan(계획) ─────┐      ┌─ Design(기획·설계) ────┐      ┌─ Impl(구현) ───────┐
 │ dev/plan/        │      │ dev/design/            │      │ dev/impl/ + 코드    │
 │ 무엇을·왜·경계    │  →   │ 단위별 상세 설계        │  →   │ 단계별 구현·검수     │
 │ 확정 vs 미결 분리 │      │ + 설계 지도(단일 소스)  │      │ (§1~§7)             │
 └──────────────────┘      └────────────────────────┘      └─────────────────────┘
        ▲                         │  설계가 바뀌면 같은 세션에서 상위 요약으로 역전파(§0-5)  │
        └─────────────────────────┴───── 구현 중 설계와 어긋나면 design을 고치고 plan까지 ─┘
```

### 0-1. 폴더와 역할

| 폴더 | 성격 | 핵심 문서 | 무엇의 단일 소스인가 |
|---|---|---|---|
| `dev/plan/` | 개요 + 앞단 진행관리 | `README`(진입점) · `overview` · `checklist` · `open-questions` | 목적·확정 결정·앞단 진행 상태 |
| `dev/design/` | 모든 설계(평면 구조) | `map`(설계 지도) · `<개념>-design`(단위별 상세) | **설계** |
| `dev/impl/` | 구현 실행 관리 | §2 | "어디까지 만들었나" |
| `dev/evidence/` | 증거·실측 | 스크린샷·전사·실측 절차 | 근거 보관 |
| `project-memory/` | 팀 공용 기록(필수 — 결정 변경·미검증 해소·절대 규칙이 모두 여기로 모인다) | `decisions` · `gotchas` | 왜 그렇게 정했나·반복 함정 |

- **`dev/plan/`에는 설계 문서를 만들지 않는다.** 설계는 `dev/design/`, `dev/plan/`은 개요·진행관리만 둔다 — 섞이면 어느 쪽이 설계의 소스인지 흐려진다.
- **단위 ID와 파일 번호는 안정 식별자다.** 단위를 합치거나 지워 번호에 구멍이 생겨도 재번호화하지 않는다.
  다른 문서가 ID로 인용하므로 재번호화는 무관한 대규모 참조 수정을 부른다. 파일명은 번호보다 의미 이름(`overview.md`)을 권장한다.
- **외부 조망도(화이트보드 사진·위키 흐름도)는 비규범**이다. 설계 지도와 달라도 되지만, 그 차이로 무엇이 달라지는지
  (어느 단위가 책임을 넘겨받는지, *(워크플로형)* 단위 사이 흐름이 어떻게 바뀌는지, 중단 후 다시 시작할 때 영향)를 적은 경우에만 허용한다.
  **외부에 부작용을 내거나, 안전 검사·*(워크플로형)* 사람 확인·대기를 맡은 단위를 합치거나 지우는 것은 별도 결정 없이 금지**(순수 계산 단위끼리 합치는 것만 허용).
- 문서를 HTML 등으로 시각화했다면 그것은 **파생물**이다. 원천 md가 바뀌면 시각화를 맞춘다(반대 아님).

### 0-2. Plan 단계 — "무엇을 만들고 무엇을 모르는가"를 고정한다

**목적**: 큰 흐름을 확정하고, 확정된 것과 미결을 갈라 놓아 이후 세션이 단위별로 이어받게 한다.
한 세션에 완성하려 하지 않는다 — plan 폴더 자체가 **핸드오프 문서**다.

**산출물**

| 문서 | 담는 것 |
|---|---|
| `dev/plan/README.md` | 새 세션 진입점(읽는 순서) · 폴더 역할표 · 향후 진행 방식 · 원천 자료 목록 · 실측 근거 요약 · **폐기된 초기 가설 목록** |
| `dev/plan/overview.md` | 목적 · 아키텍처(구성요소·소유 경계) · **배치 기준**(무엇을 독립 단위/공용 참조/인라인으로 두나) · 운영 모델 · 확정 결정·사실 |
| `dev/plan/checklist.md` | ① 역전파 체크리스트(§0-5) ② **확정**(재논의 불필요) ③ **단위별 남은 상세 설계**(각각 Design 세션 대상) ④ **외부 리뷰 보강**(필수 반영) |
| `dev/plan/open-questions.md` | ① **확보할 자료·실측** ② **남은 결정 논점** — 해소되면 체크하고 근거 링크 |

**절차**
1. **원천 자료 수집** — 규칙 문서·위키·흐름도·기존 가이드를 저장소에 모으고 경로를 README에 적는다.
2. **구성요소 분해와 배치 기준 확정** — 무엇을 독립 구성요소로 두고 무엇을 공용 모듈·인라인으로 둘지의 기준을 **문장으로** 남긴다.
   그래야 나중 판단이 흔들리지 않는다. 예: "외부 API마다 클라이언트 모듈 하나, 엔드포인트는 클라이언트를 직접 부르지 않고
   서비스 계층을 거친다", "단독으로 호출하면 안전 확인을 건너뛸 수 있는 기능은 외부에 따로 노출하지 않는다".
3. **확정과 미결 분리** — 사용자와 합의한 것만 "확정"에 넣는다. 에이전트의 추론은 확정이 아니다(§5-1).
4. **실측이 필요한 가정을 뽑아 `open-questions`로** — 외부 시스템 접근·권한·데이터 포맷처럼 "된다고 들은 것"은 실측 대상(§0-4).
5. **폐기된 초기 가설을 취소선으로 명시** — "이 문서는 최종 결정만 담는다. 아래는 되살리지 말 것".
6. **종료 조건**: 확정 목록, 단위별 상세화 대기 목록, 실측 계획, 진입점 README.

### 0-3. Design 단계 — 단위별로 플랜 모드를 다시 켜서 상세 설계를 만든다

**원칙**: 단위 하나당 플랜 모드를 새로 켜고, `dev/plan/checklist.md`의 "남은 상세 설계" 항목을 근거로
**그 단위의 상세 설계를 `dev/design/<개념>-design.md`로** 작성한다(번호 없는 개념명). 설계 문서는 **개념 하나당 하나**다 —
서로 맞물린 단위 여러 개(예: 같은 자원을 다루는 앞뒤 단위)는 한 문서에 함께 담고, 설계 지도의 "참조" 칸이 모두 그 문서를 가리킨다. 플랜 모드에서는 파일을 쓰지 않으므로,
플랜에 설계 내용(초안)을 담아 승인받은 뒤 플랜 모드를 나와 설계 문서로 옮겨 쓴다. Plan 단계(§0-2)도 같은 방식으로 플랜 모드에서 시작한다.

**한 세션의 절차**
1. "남은 상세 설계"에서 단위 하나 선택(의존 순서 — 앞 결정이 뒤의 전제를 바꾸는 것부터).
2. 읽기·조사 + 필요한 **실측**(§0-4). 사용자가 정할 것은 텍스트로 단계적으로 묻는다(한 번에 한두 개, §5-6).
3. 설계 문서 작성 — §8-5 템플릿.
4. **독립 검수**(독립 검수자, GO까지 반복 — §4-4 규칙) → 지적을 문서·코드로 확인해 반영, 반영하지 않으면 이유를 기록.
5. **역전파 체크리스트(§0-5)** 수행 — 설계 지도·overview·open-questions에 반영.
6. `dev/plan/checklist.md` 항목을 `[x]`로 하고 **한 단락 요약 + 설계 문서 링크**를 남긴다.
7. 비자명한 결정·함정은 `project-memory/`에.
8. **커밋·푸시** — 설계 문서·역전파한 문서·`dev/plan/checklist.md` 요약·`project-memory/` 기록을 **한 커밋**으로.
   구현 단계와 같은 규칙이다: **검수 GO 전에는 커밋하지 않는다**(§4-4·§4-6). 그 뒤 §7의 핸드오프 점검.

**설계 지도(`dev/design/map.md`)는 설계의 단일 소스**다. 단위마다 한 행:

| 열 | 내용 |
|---|---|
| ID | 안정 식별자 |
| 단위 | 이름 |
| 참조 | 상세 설계 문서 경로 |
| 처리 | 한 줄 요지 |
| 구현 구분 | 구현 백로그로 이어지는 열(아래) |
| *(워크플로형)* 순서·분기 | 실행 순서와 갈래 조건. 병렬인 단위(엔드포인트 등)로 이뤄진 서비스·라이브러리형은 생략하고 의존 관계만 적는다 |
| *(워크플로형)* 담당 | 누가 수행하나(예: 시스템 / 사람 / 외부 시스템). 사람이 개입하는 지점은 처리 칸에 `★사용자 개입:`으로 표시 |

- **"구현 구분" 열이 Design → Impl 계약**이다. `dev/impl/checklist.md`는 이 열을 Phase로 편성한 것이며, 백로그의 소스는 이 열이다.
  이 칸에는 "만들 모듈·API와 그 입출력 계약"을 적는다.
- 도식으로 그릴 때는 지금의 흐름·조건만 담고 이력·근거는 md에만 둔다.

**종료 조건**: "남은 상세 설계" 전 항목 `[x]`, `open-questions` 전건 해소 또는 "preflight"로 명시 이관.
(기본은 전건 완료 뒤 구현 진입이다. 예외 선택지는 §0-6 아래 주석.)

### 0-4. 실측(Evidence) 규칙 — 설계 가정을 사실로 만든다

- **사용자 진술·간접 증거는 검증이 아니다.** 설계가 기대는 외부 시스템(인증·API·메시징·권한)은 직접 호출해 확인한다.
  "검증됨"이라 적힌 문구의 실체가 진술뿐인 경우가 구현 직전 점검에서 흔히 드러난다.
- **읽기 전용 실측 먼저.** 부작용이 있는 쓰기(알림 발송·리소스 생성)는 **의도적으로 미검증으로 남기고**
  preflight로 넘긴다 — 그 사실과 이유를 문서에 적는다.
- **가설을 반증한 실측도 기록한다**(예: "이 환경에선 A 언어로만 외부 API 호출이 된다"는 가설을 직접 호출로 반증 → 언어 결정이 바뀜).
- 증거는 `dev/evidence/`에 파일로 남긴다(스크린샷·전사·실측 절차·결과). 나중에 방식이 바뀌어도
  **당시 기록 보관용**이라고 머리에 적고 지우지 않는다.
- 실측 결과가 확정 결정을 뒤집으면 관련 문서(§0-5 grep)와 `project-memory/decisions/<주제>.md`에 한꺼번에 반영한다.
- 외부 서버·문서는 시간이 지나면 바뀐다 → 실측 결과에는 날짜를 적는다.

### 0-5. 역전파 — 문서가 서로 어긋나지 않게

**역전파 체크리스트** — 단위를 상세화할 때뿐 아니라 확정 항목의 상태·성격을 바꿀 때도 매번 복사해 체크한다.
(`dev/plan/checklist.md` 맨 위에 둔다.)

- [ ] 이 변경으로 바뀐 결정이 있는가? (없으면 종료)
- [ ] **★ 식별자 grep 역전파** — 바꾼 단위·항목의 ID와 관련 파일명을 `dev/plan/`·`dev/design/`·`dev/impl/`·`project-memory/`
      전체에서 grep해 **인용처를 빠짐없이 갱신**한다. 가장 잘 빠지는 곳: 다른 설계 문서의 상호 참조, ID를 나열한 요약 표
- [ ] 설계 지도의 해당 행 한 줄 요지 갱신(또는 "변경 없음" 확인)
- [ ] `dev/plan/overview.md`의 확정 사실·전제에 영향이 있는가
- [ ] `dev/plan/open-questions.md`의 해소·신규 발생 반영(건수 표기 포함)
- [ ] 설계 지도의 "참조" 칸이 실제 문서를 정확히 가리키는가

**대체 표식**: 결정이 뒤집히면 옛 서술을 지우지 말고 `~~옛 서술~~ [대체됨 YYYY-MM-DD: 새 내용 — 링크]`로 남긴다.
변경 이력은 `decisions/<주제>.md`에, 본문은 현재 서술 위주로.

### 0-6. 단계 전환 게이트

| 전환 | 통과 조건 |
|---|---|
| Plan → Design | 확정 목록 · 단위별 상세화 대기 목록 · 폐기 가설 명시 · 진입점 README |
| Design → Impl | **설계 완료 범위**(아래 주석 — 기본 A: 모든 단위 / 선택지 B: 첫 슬라이스에 속한 단위)의 상세 설계 `[x]` · 그 범위의 외부 리뷰 보강 반영 · 그 범위의 `open-questions` 해소 또는 preflight 이관 · 역전파 grep 잔존 0, 그리고 **"구현 준비 상태 점검" 세션** 완료: ① 가정 실측(§0-4) ② 문서 간 어긋남(취소선 누락·옛 서술 혼재) 0 ③ `dev/impl/README.md`의 확정 전제 작성 ④ `dev/impl/checklist.md`가 설계 지도의 "구현 구분" 열을 Phase로 편성 |
| Impl 중 설계 충돌 | 구현이 설계와 어긋나면 `dev/impl/`이 아니라 **design을 고치고** plan까지 역전파 — 단, 사용자와 의논한 뒤에만(§5) |

> **설계 완료 범위 — 기본(A)과 선택지(B)**
> - **A. 기본 — 모든 단위의 설계를 끝낸 뒤 구현에 들어간다.** 원본 프로젝트에서 검증된 방식이다(설계 전건 완료 후 구현 착수).
>   구현 중 설계가 뒤집힐 위험이 가장 적다. §4-3의 "수직 슬라이스 우선"은 이 경우 **구현 순서**에만 적용된다.
>   구현 도중 설계에서 정하지 않은 것이 드러나면 그 단계 플랜에서 사용자와 정한다(§5-1).
> - **B. 선택지 — 첫 슬라이스에 속한 단위만 설계를 끝내면 구현에 들어간다.** 빨리 시작할 수 있지만 **원본에서 검증되지 않은 방식**이다.
>   나머지 단위의 설계가 이미 만든 구현을 바꿀 수 있으므로, 그런 변경은 그 단계 플랜에서 사용자와 정한다. 채택 여부는 §9-3 "판단한다".
>   B에서는 위 게이트 조건을 첫 슬라이스에 속한 단위에만 적용하고, 다음 슬라이스로 넘어갈 때마다 그 슬라이스의 단위에 같은 조건을 다시 적용한다.

Design 세션 하나는 Impl 단계의 "플랜 → 명세 고정"과 같은 모양이다 — 계획은 항상 문서로 남기고, 검수받고, 승인받는다.

## 1. 핵심 원칙 (한 장 요약)

| # | 원칙 | 한 줄 이유 |
|---|---|---|
| 1 | **저장소 안 문서가 유일한 기억이다** | 대화·PC·저장소 밖 플랜 파일은 다음 세션이 보장받지 못한다 |
| 2 | **모든 구현 단계는 코드 전에 플랜 모드부터** | 플랜 검수가 구현 전에 설계 구멍을 잡는다 |
| 3 | **승인된 상세 명세는 구현 전에 저장소에 고정한다** | 한 줄 요약만 있으면 새 세션이 결정을 놓친다 |
| 4 | **검수는 커밋 게이트, 통과 = GO까지 반복** | 1회 검수로 끝내면 결함이 다음 단계로 샌다 |
| 5 | **미검증은 단계마다 장부에 적고 해소되면 지운다** | 흩어지면 코드 결함까지 묻힌다 |
| 6 | **추론은 확인받고, 설계는 의논 없이 바꾸지 않는다** | 편의로 바꾼 설계는 승인까지 받고도 틀린다 |
| 7 | **범위는 빼지 말고 분할한다** | 승인된 명세를 조용히 줄이면 약속이 사라진다 |
| 8 | **커밋 뒤 "맥락 없는 독자"로 핸드오프를 점검한다** | 다음 세션이 한 줄 지시로 이어지는지 사람이 매번 확인하지 않게 |

## 2. 구현 폴더·문서 구조

`dev/impl/`은 **구현 실행 관리 전용 폴더**다. 코드는 다른 곳(`src/` 등)에 있고, 여기에는
"무엇을 어디까지 만들었나 / 다음에 뭘 하나 / 무엇이 미확인인가"만 둔다.

```
git-guide/
├─ CLAUDE.md                 # 에이전트 지침 — 이 프로세스를 가리키기만 한다 (§9-2 스니펫)
├─ README.md · VERSION       # 프로젝트 소개 · 버전 단일 소스
├─ index.html · lessons/ · assets/   # 사이트 코드 (예정 — 코드는 dev/ 밖, 루트)
├─ docs/                     # 릴리즈 운영 문서 (RELEASE_MANAGEMENT.md · UPDATE_CHECKLIST.md)
├─ dev/
│  ├─ LONG_TERM_DEV_PROCESS.md   # 이 가이드 (git-guide 적용본)
│  ├─ plan/                  # (§0-2) 개요·확정 결정·앞단 미결 — 설계 문서는 두지 않는다
│  ├─ design/                # (§0-3) 설계 지도 + 단위별 상세 설계 — 설계의 단일 소스
│  ├─ evidence/              # (§0-4) 실측 증거
│  └─ impl/
│     ├─ README.md           # 진입점: 읽는 순서 + 확정 전제 + 진행 방식
│     ├─ checklist.md        # Phase별 구현 백로그(체크박스) + 항목별 승인된 상세 명세
│     ├─ progress.md         # 핸드오프 로그: "다음 착수 지점" + 날짜별 완료 로그
│     └─ open-questions.md   # 구현 미검증·미결 장부 (ID 부여, 해소되면 삭제)
└─ project-memory/           # decisions/<주제>.md(결정) · gotchas.md(함정) · log.md 등
```

> 이 폴더들을 저장소 루트가 아니라 `docs/<작업명>/` 아래에 둘 수도 있다. 그럴 때는 이 가이드와 §9-2 스니펫의
> `plan/`·`design/`·`impl/` 경로를 실제 위치로 바꿔 적고, §6·§7 핸드오프 점검에 쓰는 지시 문장
> (`"impl/README.md를 읽고 …"`, `"plan/README.md를 읽고 …"`)의 경로도 함께 바꾼다.
>
> **이 저장소는 루트 `dev/`에 둔다** (2026-10-14 사용자 결정 — 구현이 실제 코드라 `docs`보다 `dev`). 이 적용본의 경로는 이미 `dev/…`로 바꿔 두었다.

| 문서 | 역할 | 갱신 시점 |
|---|---|---|
| `dev/impl/README.md` | 새 구현 세션의 **유일한 진입점**. 읽는 순서·확정 전제·진행 방식 | 프로세스·전제가 바뀔 때만 |
| `dev/impl/checklist.md` | 무엇을 만들지 + 항목별 **승인된 상세 명세** | 플랜 승인 직후(구현 착수 전), 단계 완료 시 `[x]` |
| `dev/impl/progress.md` | "다음 착수 지점"(한 줄 요약 + 명세 위치) + 날짜별 완료 로그 | 단계 커밋에 함께 넣고, 핸드오프 점검 결과는 추가 커밋 |
| `dev/impl/open-questions.md` | 못 확인한 것의 장부 | 단계 완료 시(커밋 전) |
| `project-memory/*` | 결정·함정의 영구 기록 | 비자명한 결정·발견 때마다 |

**우선순위 규칙**
- 저장소의 현재 상태(설계 문서·코드)가 항상 `dev/impl/`·`project-memory/` 기록보다 우선한다. 기록이 현재 상태와 충돌하면 기록을 갱신한다.
- **설계 문서와 코드가 서로 어긋나면 설계 문서가 기준**이다. 코드를 설계에 맞추거나, 설계를 바꿔야 한다면
  사용자와 의논해 확정한 뒤(§5) 설계 문서를 고치고 상위 계획으로 역전파한다. 어느 쪽이든 `dev/impl/`만 고쳐 맞추지 않는다.

## 3. 새 세션 진입 순서

`dev/impl/README.md` 맨 위에 박아 두는 읽기 순서다.

1. `dev/impl/README.md` — 진행 방식 + 확정 전제
2. `dev/impl/progress.md` — 끝난 것과 **"다음 착수 지점"** / `dev/impl/open-questions.md` — 착수할 단계에 걸린 항목이 있는지
3. `dev/impl/checklist.md` — 해당 항목의 승인된 명세
4. `dev/design/map.md`와 해당 단위의 설계 문서
5. **→ 곧장 파일을 만들지 않고 플랜 모드부터 들어간다** (§4-1)

> 사용자의 한 줄 지시 `"dev/impl/README.md를 읽고 다음 단계 진행해줘"`만으로 위 순서가 성립해야 한다.
> 성립하는지를 매 단계 끝에 §6 핸드오프 점검으로 확인한다.

## 4. 한 단계의 생애 (Step Loop)

```
 ┌───────────────────────── 한 단계(= dev/impl/checklist.md 항목 하나) ──────────────────┐
 │ 1. 맥락 잡기      README → progress → open-questions → checklist → 설계           │
 │ 2. 플랜 모드      조사 → 플랜 작성 → [플랜 검수] → 사용자 승인                    │
 │ 3. 명세 고정      승인된 상세 명세를 dev/impl/checklist.md에 반영 (승인 ↔ 구현 사이)   │
 │ 4. 구현                                                                           │
 │ 5. 테스트         단위 테스트 + 전체 스위트 결과 기록                              │
 │ 6. 구현 검수      독립 검수자 → NO-GO면 수정 → 재검수, GO까지 반복                 │
 │ 7. 미검증 정리    dev/impl/open-questions.md 추가·해소                                │
 │ 8. 로그           dev/impl/progress.md에 날짜·완료분·다음 착수 지점                    │
 │ 9. 커밋·푸시      코드 + 문서 + 로그를 한 커밋으로. GO 전에는 하지 않는다          │
 │10. 핸드오프 점검  맥락 없는 서브에이전트로 확인 → 결과 기록을 추가 커밋·푸시       │
 └───────────────────────────────────────────────────────────────────────────────────┘
```

### 4-1. 플랜 모드 (코드 전 필수)

- "다음 단계 진행해줘" 류 요청을 받으면 **읽기·조사 후 바로 구현하지 않고** 플랜 모드로 들어간다.
  새 단계를 시작하는 요청이면 사용자에게 묻지 말고 곧바로 들어간다.
- 순서: **조사 → 플랜 작성 → 플랜 검수 → 사용자 승인**.
- 플랜에 사용자가 정할 것이 있으면 §5-6 방식으로 묻고, 확정되면 날짜·사용자 원문과 함께 플랜에 적는다.
- **예외는 둘뿐**: ① 오탈자·문서 한 줄처럼 코드 판단이 없는 사소한 변경 ② 사용자가 "승인된 플랜 그대로 구현"이라고
  지시한 경우. ②도 **구현 전에 `dev/impl/checklist.md`의 상세 명세를 먼저 읽는다.** 저장소에 상세 명세가 없으면
  (저장소 밖 플랜 파일은 다음 세션이 보장받지 못한다) 예외를 쓰지 말고 플랜 모드부터 들어간다.

### 4-2. 승인 직후 명세 고정

플랜 승인 → 구현 착수 **사이**에 `dev/impl/checklist.md` 해당 항목에 반영한다.

- 입출력 스키마, 상태·분기 규칙, 플랜 검수에서 나온 결정, 사용자 결정, 테스트 케이스, 스모크 기준
- `dev/impl/progress.md`의 "다음 착수 지점"에는 **한 줄 요약 + 명세 위치**만 둔다(상세 복사 금지 — 두 곳에 두면 어긋난다).

### 4-3. 구현·테스트

- **계약 우선**: 모듈이 내보내는 출력(스키마)을 먼저 고정하고, 소비하는 쪽은 그 계약만 본다.
- **수직 슬라이스 우선**: 가장 작은 흐름 하나를 처음부터 끝까지 먼저 구현해 계약(*(워크플로형)* 상태 저장·재개 포함)을 일찍 검증한 뒤 넓힌다
  (구현 순서의 원칙이다 — 설계를 어디까지 끝내고 들어오는지는 §0-6 아래 주석 A/B).
- 테스트 필수. 전체 스위트 결과(개수, 무작위 순서·시드를 쓰면 그 값)를 로그와 검수 요청에 남긴다.
- 실환경 부작용이 있는 스모크는 **사전 상태 기록 → 승인된 스모크 → `finally`로 정리 → 원상복구 확인**을 한 세트로 한다.
  원상복구 확인 항목은 대상에 맞게 정한다(예: 파일이면 사전 해시 일치, 서버 자원이면 이번에 만든 임시 리소스가 남지 않음, 서비스면 테스트 계정 상태 복원).
  스모크 표준 대상(파일·테스트 계정·스테이징 환경 등)을 정해 두고, 바꿀 때는 사용자가 정한다.
- **되돌릴 수 없는 외부 쓰기**(메시지 게시·알림 발송 등)는 원상복구가 안 되므로 실환경 스모크를 하지 않는다.
  preflight로 미뤄 미검증 장부에 올린다(§0-4).

### 4-4. 구현 검수 — 커밋 게이트, GO까지 반복

- 방금 구현한 모듈·테스트를 **독립 검수자**에게 넘겨 리뷰받는다. 통과 없이 다음 단계로 가지 않는다.
- 이 절의 규칙(GO까지 반복·재검수 범위 한정)은 **플랜 검수에도 똑같이** 적용한다.
- **통과 = 검수자가 GO**(P0·P1 없음). NO-GO면 **지적을 코드로 확인해 반영 → 같은 절차로 재검수**를 GO까지 반복한다.
- **재검수 범위는 직전 지적의 해소 확인으로 좁힌다**: 직전 지적 목록과 수정 위치를 넘기고, 판정 대상은
  ① 지적이 해소됐는가 ② 그 수정이 같은 지점에 만든 회귀뿐이다. 범위 밖에서 새로 보인 결함은 GO/NO-GO에 넣지 않고
  보고만 받아 `dev/impl/open-questions.md`에 기록한다(다음 단계 검수로 넘김). "새 결함도 찾아 달라"고 하면 회차마다 범위가
  넓어져 끝나지 않는다.
  - **예외 — 범위 밖 P0**: 범위 밖 결함이 P0이고 **코드로 재현·확인된 경우에만** 새 지적으로 받아 수정한 뒤 재검수한다
    (GO 전이므로 커밋하지 않는다). 재현되지 않은 P0 주장과 범위 밖 P1·P2는 위대로 장부에 기록만 한다.
    범위가 넓어진 원인이 재현되지 않는 가장자리 사례였으므로 재현 조건으로 거른다. *(원본 운영에서 범위 밖 P0가
    나온 적이 없어 이 예외는 검증되지 않았다.)*
- P2만 남은 GO는 반영하거나 **반영하지 않는 이유를 기록**한다.
- **GO 전에는 커밋하지 않는다**(이미 했다면 GO까지 푸시하지 않고, 수정분은 GO 뒤 추가 커밋).
- 수정분을 재검수 없이 회귀 테스트로만 고정하지 않는다. 검수자가 사용량 한도 등으로 못 하는 경우만 예외이며,
  이유와 대상을 `dev/impl/open-questions.md`에 적고 사용자에게 알린다.
- 검수자가 테스트를 직접 못 돌리면 내 쪽 전체 스위트 결과를 요청에 넣는다.
- 검수자의 지적도 **코드·실행 경로로 확인한 뒤** 사용자에게 전달한다(검수자 오탐 방지).
- 검수자 모델·설정을 지정해 쓴다면, 실제로 그 설정으로 실행됐는지 실행 기록으로 확인하고 로그에 남긴다.

### 4-5. 미검증 정리 (커밋 전)

`dev/impl/open-questions.md`에 아래를 정리한다. **이번 단계로 해소된 항목은 지우고** 확인 결과를
`gotchas.md`(사실·함정)/`decisions/<주제>.md`(정책 변경)로 옮긴다. `dev/impl/progress.md`에는 항목을 복사하지 않고
추가·해소한 **ID만** 적는다.

| 대상 | 예 |
|---|---|
| ① 실환경에서 못 본 경로 | 모킹·임시 데이터·합성 데이터로만 확인 |
| ② 검수의 빈틈 | 검수자가 테스트를 못 돌림, 재검수 못 받은 수정분 |
| ③ 외부 규칙 의존 가정 | 서버 정책·권한·조직 규칙·외부 시스템 동작 |
| ④ 부작용 때문에 미룬 실행 | 위험해서 못 돌린 스모크(preflight) |
| ⑤ 미이행 | 해야 하는데 아직 안 한 것 |

### 4-6. 로그·커밋

- **커밋 전에** `dev/impl/progress.md` 맨 위에 새 로그를 추가하고 "다음 착수 지점"을 갱신한다(§8-2). 로그는 코드·문서와 **같은 커밋**에 넣는다
  (커밋 해시는 아직 모르므로 로그 제목에는 다음 커밋 때 채워 넣는다).
- 커밋 단위는 **항목 단위**를 권장한다. 한 단계는 보통 커밋 1개 + 핸드오프 점검 결과 커밋 1개(§6에서 문서를 고쳤다면 그 수정 커밋)로 끝난다.

## 5. 설계 수호 규칙 (모든 단계 공통)

아래 규칙은 이 문서에서 `§5-1`~`§5-7`로 인용한다.

- **5-1. 추론은 확인받는다.** 문서·코드에 명시되지 않은 값·정책을 추론했다면 플랜·명세·코드·문서에 반영하기 **전에**
   사용자에게 확인한다. 플랜의 "가정" 절에 적어 두는 것으로 갈음하지 않는다.
- **5-2. 설계(단위 구성·의존, *(워크플로형)* 분기·사람 개입 지점·순서)는 사용자와 의논해 확정한 뒤에만 바꾼다.** 에이전트의 추론만으로는 근거가 안 된다.
- **5-3. 설계 변경의 근거는 둘뿐**: 기존 설계의 구조적 문제, 또는 변경으로 생기는 구조적 개선.
   **설계·구현 편의는 근거가 아니다.** 편의로 단위를 합치거나 빼거나 비워 두지 않는다.
- **5-4. 아직 구현되지 않은 단위는 건너뛰지 않고 그 앞에서 멈추게 만든다.** 일부만 구현된 상태의 시스템이
  미구현 단위에 이르면, 빈 통과 처리(아무것도 안 하고 다음으로 넘기는 stub)로 지나가지 말고 "미구현"을 알리며 명시적으로 멈추게 한다.
   개발 순서도 같다 — 막혔다고 그 단위를 비워 둔 채 뒤 단위로 넘어가지 않는다. (작업을 여러 단계로 나누는 것은 설계 변경이 아니다.)
- **5-5. 범위는 빼지 말고 분할한다.** 플랜의 문서·부수 작업은 항목마다 "이번 단계에 꼭 필요한가"를 판정한다.
   ① 코드와 같은 커밋이어야 하는 것만 이번에 넣고 ② 나머지는 **다음 단계로 분할**해 `dev/impl/checklist.md`에 옮겨 적고
   ③ 승인된 명세의 항목을 사용자 결정 없이 장부 한 줄로 대체하지 않는다.
- **5-6. 정책·설계 질문은 선택지 UI로 한꺼번에 묻지 않고 텍스트로 단계적으로** 묻는다 — 한 번에 한두 개, 의존 순서대로.
   질문마다 ① 확인한 사실(근거 `파일:줄`) ② 왜 정해야 하나 ③ 가능한 방법과 장단점 ④ 권장과 근거. 사용자가 되물으면 답부터 하고,
   질문에 대한 답을 결정으로 바꾸지 않으며, 사용자 답의 적용 범위를 넓히지 않는다.
- **5-7. "절대 규칙"은 구두로만 두지 않는다.** 말로만 지시된 규칙은 기록되지 않아 사라진다 →
   `CLAUDE.md` + `decisions/<주제>.md`(+ 해당 명세)에 날짜와 함께 적고, 만든 계기(위반 사례)도 한 줄 남긴다.

## 6. 핸드오프 점검 (커밋·푸시 뒤 매 단계 마지막)

**목적**: 새 세션에서 `"dev/impl/README.md를 읽고, 다음 단계 진행해줘."` 한 줄만으로 올바른 다음 단계에 착수할 수 있는지 확인한다.

**방법**: 현재 대화의 맥락을 **물려받지 않는** 서브에이전트에게 읽기 전용으로 위 문장을 그대로 주고,
"실행하지 말고 ▸ 무엇을 읽고 ▸ 어떤 단계를 어떤 절차(플랜 모드 여부 포함)로 시작할지 ▸ 먼저 읽을 문서 ▸
막히거나 모호한 점"만 보고하게 한다.

**판정 기준 (전부 만족해야 통과)**

1. 다음 단계를 `dev/impl/progress.md`의 "다음 착수 지점"과 같게 짚는다
2. 플랜 모드부터 들어간다고 답한다
3. 먼저 읽을 문서·명세(`dev/impl/checklist.md` 항목, `dev/impl/open-questions.md` ID)를 찾아낸다
4. 이미 끝난 단계·지운 ID·옛 명령을 **현재 할 일로 읽지 않는다**
5. 점검 시작 시점에 `git status`가 깨끗하고 원격과 같다(커밋·푸시 누락 없음)

어긋나면 **원인 문서를 고쳐 커밋·푸시한 뒤 같은 점검을 다시** 한다(코드 판단이 없는 문서 수정이라 플랜 모드·검수 없이 진행).
통과하면 결과(통과·고친 곳)를 `dev/impl/progress.md`의 그 단계 로그에 한 줄로 남기고 **추가 커밋·푸시**한다 —
이 기록 커밋은 점검 대상이 아니므로 다시 점검하지 않는다.

> 흔한 어긋남: 완료 전 상태를 서술한 구절이 남아 있음 / "다음 착수 지점"이 아직 정하지 않은 결정을 단정함 /
> 옛 명령·지운 ID가 현재 지침처럼 읽힘 → 대체 표식을 달거나 갱신한다.

## 7. 단계 루프를 Design 단계에도 쓰기

§4의 루프는 구현 전용이 아니다. Design 세션(§0-3)도 같은 모양으로 굴린다.

| 구현 단계 | Design 세션의 대응 |
|---|---|
| 플랜 모드 + 플랜 검수 | 단위 하나에 대한 플랜 모드 + 설계 문서 독립 검수 |
| 명세 고정(`dev/impl/checklist.md`) | 설계 문서(`dev/design/<개념>-design.md`) + `dev/plan/checklist.md` 요약 |
| 미검증 정리(`dev/impl/open-questions.md`) | `dev/plan/open-questions.md`의 실측·결정 논점 |
| 문서 역전파 | 역전파 체크리스트(§0-5) |
| 커밋·푸시(GO 뒤, 한 커밋) | 같은 규칙 — 설계 문서·역전파 문서·요약·기록을 GO 뒤 한 커밋으로(§0-3 8) |
| 핸드오프 점검 | `"dev/plan/README.md를 읽고 다음 설계 진행해줘"`로 같은 점검(§6 기준을 plan 문서로 바꿔 적용) |

### 9-2. `CLAUDE.md` 스니펫

```markdown
## 계획·설계·구현 작업 원칙 (상세: dev/LONG_TERM_DEV_PROCESS.md)

- **단위 설계는 단위별 플랜 모드로 `dev/design/<개념>-design.md`에 쓴다.** `dev/plan/`에는 설계 문서를 만들지 않는다.
  설계·확정 항목을 바꾸면 같은 세션에서 `dev/plan/checklist.md`의 역전파 체크리스트로 상위 문서에 반영한다(식별자 grep).
- 외부 시스템 동작에 기대는 설계 가정은 사용자 진술이 아니라 직접 실측으로 확인하고, 부작용 있는 쓰기는 미검증으로 명시해 preflight로 넘긴다.
- **`dev/impl/`의 구현 단계("다음 단계 진행해줘" 류)는 코드를 쓰기 전에 반드시 플랜 모드부터 거친다.**
  단계 전체 순서(플랜 검수·구현·테스트·구현 검수·미검증 정리·커밋·핸드오프 점검)는 `dev/impl/README.md` "진행 방식" 한 곳에만 둔다.
  새 단계를 시작하는 요청이면 묻지 말고 곧바로 플랜 모드로 들어간다(예외: 사소한 문서 수정, 또는 사용자가
  "승인된 플랜 그대로 구현"이라고 지시한 경우 — 이때도 `dev/impl/checklist.md`의 상세 명세를 먼저 읽는다).
- **★ 절대 규칙 — 추론은 확인받고, 설계는 의논 없이 바꾸지 않는다.** 명시되지 않은 값·정책을 추론했으면 반영 전에
  사용자에게 확인한다. 설계 변경의 근거는 구조적 문제·구조적 개선뿐이며 설계·구현 편의는 근거가 아니다.
  아직 구현되지 않은 단위 앞에서는 멈추고 건너뛰지 않는다.
- 각 단계는 **독립 검수 GO 전에는 커밋·푸시하지 않는다.** NO-GO면 수정 후 같은 절차로 재검수한다.
- 단계 완료 시(커밋 전) 미검증 사항을 `dev/impl/open-questions.md`에 정리하고 `dev/impl/progress.md` 로그와 함께 단계 커밋에 넣는다.
  커밋·푸시 뒤에는 핸드오프 점검을 하고, 결과를 추가 커밋·푸시한다.
- 저장소의 현재 상태(설계 문서·코드)가 항상 `dev/impl/`·`project-memory/` 기록보다 우선한다 — 충돌하면 기록을 갱신한다.
  설계 문서와 코드가 어긋나면 설계 문서가 기준이다.
```

### 9-3. 그대로 둘 것 / 바꿀 것

| 구분 | 내용 |
|---|---|
| **그대로 둔다** | 단계별 폴더 분리(plan·design·impl), 확정/미결 분리, 역전파 체크리스트, 실측 규칙, 단계 루프(§4), 검수 게이트·GO 반복·재검수 범위 한정, 미검증 장부, 핸드오프 점검, 설계 수호 규칙(§5) |
| **바꾼다** | 단위의 정의, 확정 전제(언어·외부 시스템·절대 규칙), 스모크 표준 대상·원상복구 항목, 검수자(모델·호출 방식), 미검증 구획 이름, 기간 한정 예외(예: "개발 기간에는 어떤 부수 작업을 생략한다"처럼 사용자가 정한 예외 — 정하면 `dev/impl/README.md` 확정 전제에 적는다) |
| **판단한다** | 설계 완료 범위(기본 A = 전건 완료 후 구현 / B = 첫 슬라이스 단위만 설계 후 구현 — B는 원본에서 검증되지 않음, §0-6 아래 주석), 검수 회차(플랜 n회 + 구현 n회), 커밋 단위(항목 vs Phase), 훅 도입 여부, 폴더 위치(루트 vs `docs/<작업명>/` 아래) |

> **이 가이드가 다루지 않는 것**: 배포·CI·환경 분리·운영 모니터링 같은 출시 이후 절차. 원본 프로젝트가 그 단계까지 운영되지 않아
> 검증된 절차가 없다. 필요하면 프로젝트에서 별도로 정한다.

## 10. 흔한 실패와 대응

| 실패 | 증상 | 대응 |
|---|---|---|
| 플랜 없이 구현 진입 | 사용자 지적으로 되돌림 | §4-1 — `dev/impl/README.md` 맨 위 ⚠️ + `CLAUDE.md` 한 줄 |
| 명세가 한 줄 요약뿐 | 새 세션이 핵심 결정을 놓치고 어긋나게 구현 | §4-2 — 승인 직후 `dev/impl/checklist.md`에 상세 명세 고정 |
| 플랜 범위 과대 | 줄이려다 승인된 명세를 결정 없이 지우려 함 | §5-5 — 빼지 말고 단계 분할 |
| 재검수 범위 확대 | 회차마다 새 결함을 찾아 끝나지 않음, 재현 안 되는 가장자리 사례만 반복 | §4-4 — 직전 지적 해소 + 회귀로 한정(코드로 재현된 범위 밖 P0만 예외) |
| 미검증이 흩어짐 | 대화 요약·로그·함정 문서에 분산, 수십 건이 쌓여 코드 결함까지 묻힘 | §4-5 — 단계마다 장부로 일원화 |
| 구두 규칙 소실 | 말로만 지시한 규칙이 사라지고 그 사이 위반 구현 | §5-7 — `CLAUDE.md` + `decisions/<주제>.md`에 날짜와 함께 |
| 편의로 설계 변경 | 단위 합치기·비우기를 승인까지 받음 | §5-1~4 — 추론 확인, 의논 후 변경 |
| 핸드오프 문서 낡음 | 완료된 단계를 현재 할 일로 읽음 | §6 — 맥락 없는 서브에이전트로 점검 |
| 검수 도구 장애 | 검수가 진행되지 않거나 사용량 한도 초과 | 같은 설정으로 다시 요청하고 실행 기록으로 실제 설정 확인. 끝내 못 받으면 §4-4 예외(이유·대상을 장부에 적고 사용자에게 알림) |
| 하위 문서만 고치고 상위 미갱신 | 설계 지도 요지가 사라진 채 방치, 인용처 누락 | §0-5 — 식별자 grep 역전파를 체크리스트로 강제 |
| "검증됨"의 실체가 진술 | 실측 없이 설계가 외부 시스템 동작에 기댐 | §0-4 — 직접 호출 실측, 쓰기는 preflight로 명시 |
| 폐기된 가설이 되살아남 | 옛 서술이 남아 옛 방식으로 구현 | §0-2·§0-5 — 취소선 + `[대체됨 날짜]`, README에 폐기 목록 |
