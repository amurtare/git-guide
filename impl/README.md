# git-guide 구현 — 진행 관리 (impl/)

여러 세션에 걸쳐 레슨과 공용 도식을 단계별로 구현하기 위한 진행 관리 폴더다.
코드는 `index.html` · `lessons/` · `assets/`에 있고, 여기에는 **무엇을 어디까지 만들었나 / 다음에 뭘 하나 / 무엇이 미확인인가**만 둔다.
프로세스 원문: 사용자가 제공한 "장기 단계별 구현 프로세스 가이드"(perforce-ax-template `impl/process-guide.md`)를 이 프로젝트에 맞게 옮겼다.

## 시작하기 — 구현 세션 진입점

> ⚠️ **새 단계는 코드(HTML/CSS/JS) 작성 전에 반드시 플랜 모드(`EnterPlanMode`)부터.** 플랜을 작성 → 검수 → 사용자 승인받은 뒤 구현한다.

읽는 순서:
1. 이 파일 — 확정 전제 + 진행 방식
2. [progress.md](progress.md)의 **"다음 착수 지점"** / [open-questions.md](open-questions.md) — 착수할 단계에 걸린 항목이 있는지
3. [checklist.md](checklist.md) — 해당 항목의 승인된 명세
4. 설계 문서 — `docs/design/` (아래 "설계 문서" 참고)
5. → 곧장 파일을 만들지 않고 **플랜 모드**로 들어간다

> 사용자의 한 줄 지시 **"impl/README.md를 읽고 다음 단계 진행해줘"**만으로 위 순서가 성립해야 한다.

## 확정 전제

### ★ 절대 규칙

| # | 규칙 | 날짜 · 근거 |
|---|---|---|
| R1 | **모든 도식은 로컬·리모트 두 공간을 공용 틀로 쓴다.** 레슨마다 새 화면을 만들지 않고, 같은 틀에서 필요한 부분을 켜고 끈다 | 2026-10-13 사용자 지시 · [decisions/curriculum-foundations.md](../project-memory/decisions/curriculum-foundations.md) |
| R2 | **0단계는 Git 설명 전에 로컬/서버 버전 관리 개념부터 설명한다** | 2026-10-13 사용자 지시 · 같은 문서 |
| R3 | **추론은 확인받고, 설계는 의논 없이 바꾸지 않는다.** 설계 변경 근거는 구조적 문제·구조적 개선뿐이며 구현 편의는 근거가 아니다 | 2026-10-13 프로세스 도입 |
| R4 | **빌드 없이 `index.html`을 `file://`로 열어 동작해야 한다.** `fetch`·ES 모듈 금지, 외부 스크립트는 정확한 버전이 고정된 CDN만 | 프로젝트 출범 · [gotchas.md](../project-memory/gotchas.md) |

### 실행 환경

- 정적 HTML/CSS/JS. 학습 콘텐츠는 한국어
- 대상 브라우저: 최신 Chrome · Firefox · Safari, 모바일 폭(약 375px), 라이트/다크 모드
- **스모크 표준 대상**: `index.html` (생기기 전에는 `lessons/00-*.html`)
  - 절차: Chromium(Playwright, 컨테이너에 설치됨)으로 `file://` 열기 → 콘솔 에러 0 · 404 0 확인 → 데스크톱/모바일 폭 스크린샷 → 핵심 인터랙션 1회 조작
  - 원상복구 확인: 저장소에 남는 산출물 0개(스크린샷·임시 파일은 스크래치 디렉터리에만), `git status` 깨끗함
- **검수자**: Codex 또는 Copilot 플러그인이 설치돼 있으면 그것(플랜 종료 hook이 자동 요청). 없으면 이 대화 맥락을 물려받지 않는 새 서브에이전트. 지정 모델은 미정 → [open-questions.md C1](open-questions.md#c1-검수자-지정-모델)

### 설계 문서

- **설계의 단일 진실 소스는 `docs/design/`** 이다. 구현 중 설계와 어긋나면 `impl/`을 맞추지 말고 설계 문서를 먼저 고친다(사용자와 의논 후, R3).
- `docs/design/`이 채워지기 전(Phase 0 완료 전)까지는 [README.md](../README.md) 커리큘럼 표 + [decisions/curriculum-foundations.md](../project-memory/decisions/curriculum-foundations.md)가 설계 기준이다.
- 저장소의 현재 상태(설계 문서·코드)가 항상 `impl/` 기록보다 우선한다. 충돌하면 기록을 갱신한다.

## 진행 방식

이 순서의 원문은 **여기 한 곳**에만 둔다.

### 한 단계의 생애 (= checklist 항목 하나)

```
 1. 맥락 잡기      README → progress → open-questions → checklist → 설계 문서
 2. 플랜 모드      조사 → 플랜 작성 → [플랜 검수] → 사용자 승인
 3. 명세 고정      승인된 상세 명세를 checklist.md에 반영 (승인 ↔ 구현 사이)
 4. 구현
 5. 자동 확인      스모크 + (도입 후) 자동 테스트. 결과를 기록
 6. 구현 검수      독립 검수자 → NO-GO면 수정 → 재검수, GO까지 반복
 7. 미검증 정리    open-questions.md 추가·해소
 8. 커밋·푸시      GO 전에는 하지 않는다
 9. 로그           progress.md에 날짜·완료분·다음 착수 지점
10. 핸드오프 점검  맥락 없는 서브에이전트로 "다음 단계 진행해줘"가 통하는지 확인
```

### Phase 0(설계 문서만 만드는 단계)에서는

- 5. 자동 확인(스모크)은 대상 파일이 없으므로 생략한다.
- 6. 구현 검수는 **문서 검수**로 한다: 설계 문서가 R1~R4, 사용자와 합의한 내용, open-questions 해소 결과와 일치하는지를 독립 검수자가 판정한다.
- 플랜 검수자는 C1이 정해지기 전까지 "실행 환경"의 임시 방식(맥락 없는 새 서브에이전트)을 쓴다.

### 1~2. 플랜 모드 (코드 전 필수)

- "다음 단계 진행해줘" 류 요청이면 묻지 말고 곧바로 `EnterPlanMode`로 들어간다.
- 순서: 조사 → 플랜 작성 → 플랜 검수 → `ExitPlanMode` 승인.
- **예외는 둘뿐**: ① 오탈자·문서 한 줄처럼 판단이 없는 변경 ② 사용자가 "승인된 플랜 그대로 구현"이라고 지시한 경우.
  ②도 구현 전에 `checklist.md`의 상세 명세를 먼저 읽고, 저장소에 명세가 없으면 예외를 쓰지 않는다.
- 레슨 플랜에는 반드시 넣는다: 학습 목표, 장면(화면) 순서, 공용 틀에서 켜는 영역(R1), 인터랙션과 초기화 동작, 레슨에 나오는 Git 명령의 실제 실행 결과.

### 3. 승인 직후 명세 고정

`ExitPlanMode` 승인 → 구현 착수 **사이**에 `checklist.md` 해당 항목에 적는다. 플랜 파일은 세션 밖이라 다음 세션이 볼 수 없다.

- 장면 목록, 도식 상태 전이(명령 → 화면 변화), 공용 컴포넌트와의 계약(설정 형식), 플랜 검수에서 나온 결정, 확인 기준
- `progress.md`의 "다음 착수 지점"에는 **한 줄 요약 + checklist 위치**만 둔다(상세 복사 금지).

### 4~5. 구현·자동 확인

- **계약 우선**: 공용 도식 컴포넌트가 받는 설정 형식(공간·영역·커밋 그래프 상태)을 먼저 고정하고, 레슨은 그 계약만 쓴다.
- **수직 슬라이스 우선**: 공용 틀 + 레슨 한 장면을 끝까지 먼저 완성해 `file://` 동작과 계약을 조기 검증한 뒤 확장한다.
- 레슨의 Git 명령은 실제 Git으로 실행해 결과가 설명·도식과 맞는지 확인한다.
- 스모크는 위 "실행 환경"의 절차대로 하고 원상복구까지 확인한다. 자동 테스트 도구는 미정 → [open-questions.md C2](open-questions.md#c2-자동-확인-도구)

### 6. 구현 검수 — 커밋 게이트, GO까지 반복

- 방금 만든 파일과 스모크 결과를 독립 검수자에게 넘긴다. **통과 = GO**(P0·P1 없음).
- NO-GO면 지적을 코드·브라우저로 확인한 뒤 반영 → 같은 절차로 재검수.
- **재검수 범위는 직전 지적의 해소 + 그 수정이 만든 회귀로 좁힌다.** 범위 밖 새 결함은 판정에 넣지 않고 `open-questions.md`에 기록한다.
- P2만 남은 GO는 반영하거나 반영하지 않는 이유를 기록한다.
- 검수자가 브라우저를 못 돌리면 내 스모크 결과(콘솔 로그·스크린샷 설명)를 프롬프트에 넣는다.

### 7. 미검증 정리 (커밋 전)

`open-questions.md` 운영 규칙대로 추가·해소한다. 해소된 항목은 지우고 결과를 `project-memory/gotchas.md`(사실) 또는 `project-memory/decisions/`(정책)로 옮긴다. `progress.md`에는 ID만 적는다.

### 8~9. 커밋·로그

- 커밋 단위는 checklist 항목 단위. GO 전에는 커밋하지 않는다.
- `progress.md` 맨 위에 로그를 추가하고 "다음 착수 지점"을 갱신한다.
- **단계 완료 ≠ 릴리즈.** 레슨 하나가 완성되면 [docs/UPDATE_CHECKLIST.md](../docs/UPDATE_CHECKLIST.md)로 MINOR 릴리즈를 따로 진행한다(사용자 요청 시).

### 10. 핸드오프 점검 (커밋·푸시 뒤)

맥락을 물려받지 않는 새 서브에이전트에 **"impl/README.md를 읽고, 다음 단계 진행해줘."**를 그대로 주고, 실행하지 말고 무엇을 읽고 어떤 단계를 어떤 절차로 시작할지, 막히는 점만 보고하게 한다.

통과 기준 (전부):
1. 다음 단계를 `progress.md`의 "다음 착수 지점"과 같게 짚는다
2. 플랜 모드부터 들어간다고 답한다
3. 먼저 읽을 문서·명세(checklist 항목, open-questions ID)를 찾아낸다
4. 끝난 단계·지운 ID를 현재 할 일로 읽지 않는다
5. `git status`가 깨끗하고 원격과 같다

어긋나면 원인 문서를 고쳐 커밋·푸시하고 다시 점검한다. 결과는 `progress.md` 그 단계 로그에 한 줄 남긴다.

## 설계 수호 규칙

1. 문서·코드에 없는 값·정책을 추론했다면 반영 **전에** 사용자에게 확인한다. 플랜의 "가정" 절로 갈음하지 않는다.
2. 설계(커리큘럼 순서, 장면 구성, 공용 틀의 공간·영역)는 의논해 확정한 뒤에만 바꾼다.
3. 아직 구현되지 않은 단계 앞에서는 멈추고 건너뛰지 않는다.
4. **범위는 빼지 말고 분할한다.** 승인된 명세를 사용자 결정 없이 줄이지 않고, 다음 항목으로 나눠 `checklist.md`에 적는다.
5. 정책·설계 질문은 선택지 UI보다 텍스트로 충분히 설명해 묻는다. 질문을 결정으로 바꾸지 않는다.
6. 말로만 지시된 절대 규칙은 이 파일의 표 + `CLAUDE.md` + `project-memory/decisions/`에 날짜와 함께 남긴다.
